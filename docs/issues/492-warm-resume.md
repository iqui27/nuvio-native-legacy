# Issue 492 — warm resume and optional player retention

Two independent local settings sit together in Playback. `Retomada rápida ao voltar` is on by default. `Manter o vídeo pronto ao sair` stays off by default; its separate duration is 2, 5, 10, 30 minutes or unlimited. Existing settings keys and indices are preserved (new entries are appended).

Warm resume releases the player normally, including the existing sub-second Android exit flight. The island reopens the saved source through fontevolta and restores the saved position. Android progressive HTTP sources reuse the last title's Media3 disk cache when `Guardar o trecho baixado no disco` has a nonzero size. That size still defaults to off; warm resume does not silently enable disk allocation. HLS/DASH and live channels have no disk-cache contract. The saved cache is limited to one title/source and three hours, is dropped on profile switch, different title/source/cache size, toggle off, process exit, or less than 512 MB free. Old process folders are cleared at startup. The Home trailer leaves this slot alone.

Focusing Resume starts a cancelable root HEAD in the existing native connection pool (DNS/TCP/TLS only). Moving focus away, closing the modal, another island action, opening playback, profile switch or app suspension cancels the job. No player or decoder is created. webOS and native Tizen use this pool. Tizen WGT retains the existing no-op network warmup: browser connections are managed by the browser.

Android captures one 480-pixel-wide bitmap from the video Surface via asynchronous PixelCopy during exit, shows it under the SDL hole on island Resume and removes the ImageView on the first real frame. Capture never delays exit or keeps the decoder alive. Failure falls back to the normal opening screen. Late capture results are invalidated on profile/title/toggle changes; the bitmap expires after three hours. Snapshot success, HDR colors and PixelCopy latency still need device verification.

webOS and Tizen have no app-controlled progressive VOD disk cache and no last-frame capture API in their current native backends. They retain the saved source/position and opening-screen fallback. P2P files belong to the torrent motor, not this HTTP cache, and remain outside this change.

With both settings on, the held player wins while it exists. Its release preserves the source and Android cache/snapshot for warm resume. Unlimited never expires by timer. New playback, profile/account change, backend resource loss, app suspension/termination and low memory still release it. The existing Home rule is unchanged: **skip the Home trailer while a player is held**, including unlimited. Opening a title page releases the hold before another trailer can use the decoder. Android trim events enter the SDL low-memory path; native Tizen hosts forward pause/low-memory into SDL; webOS uses SDL lifecycle plus the existing MemAvailable <150 MB threshold sampled every three seconds. WGT forwards visibility changes into SDL; no portable browser low-memory callback exists.

Offline host checks cover cache bytes kept/reused/dropped, saved source survival, timer/unlimited/cycle releases, focus cancellation, snapshot show/hide/invalidation and Home trailer behavior. Android compiles against cached android-35/Media3; native Samsung hosts compile against cached API4/8/9/11; WGT/native main and network code receive offline syntax checks. No packaging, network, push or deployment is part of this job.

There is no device video decoder in the host harness. Measure Resume-to-first-frame on TCL using `[player] onRenderedFirstFrame ... loadMs=...` plus the existing player resume timing logs, comparing cold, warm and held returns for the same source/position. Record cache socket-byte differences and successful snapshot capture separately; a bitmap appearing is not proof of the first decoded frame.
