# AIOStreams control area — 2.1 plan

Research only, 2026-10-19. Local base: `3b988dc4273563297b0a159c8d1629abae1db4b2`, branch `agente/205-aiohub`.

Owner request, literal: **“queria uma area exclusiva do aiostream para controlar tudo”**. `DECISOES.md`, Release and version, explicitly assigns this to 2.1 and overrides the prohibition on TV config writes in `PLANO-ECOSSISTEMA.md` §7. This plan permits deliberate config writes. It does not authorize implementation or release. English follows the task's final language override.

**Recommendation:** one dedicated native area, reached from Settings / Integrations and the installed addon's menu. Reuse Settings lists, selectors, confirmation and QR sheets. Start with identification/status, then safe full-config updates, then bounded controls. Keep the server's formatter, SEL/CEL interpreters, template wizard and provider integrations on the server/configure page. No new backend, SDK, dependency or parallel settings engine.

### Auth vocabulary and material discrepancies

All paths below are relative to the user's verified instance base, including any deployment path prefix. Never hardcode the public author's instance for authenticated calls.

- **C:** configuration credentials, `Authorization: Basic base64(uuid:rawPassword)`. Split decoded Basic on the first colon only. Raw password stays in memory for the editing session. Current User routes call `resolveConfigCredentials(..., {allowEncrypted:false})`. A valid **configuration-session cookie** can substitute when supported and no Authorization header is sent. This is separate from an operator login.
- **I:** encrypted password embedded in the installed manifest URL. It is an opaque bearer credential, not a password hash to reverse. Current Search accepts it in Basic; current User GET/PUT rejects it. **Docs say User API accepts both raw and encrypted passwords; inspected source does not.** Detection alone therefore grants playback/status access, not config editing. Do not try an encrypted token on every User endpoint or persist a raw password to make detection seamless.
- **O:** operator session from `/api/v1/auth/login` or browser OIDC. Protected instances can require this in addition to C when saving/previewing config. User GET strips `accessKey`; PUT injects it only with O, then Store enforces `assertConfigAccessKey`. Never ask for/copy `CONFIG_ACCESS_KEY`, an administrator password, or the instance `SECRET_KEY`. Use the configure page when this gate cannot be satisfied through supported login.
- **J:** media-server user token acquired through Jellyfin authentication/Quick Connect; distinct from C, I and O. Do not infer management permission from it. Extension endpoints refuse Jellyfin API keys.
- **URL:** installed addon's own configured URL is the bearer credential for Stremio resources. It may contain I, an alias, and variant selection.
- **Public:** no route-level credentials in inspected source; an external reverse proxy can still require login.

User envelopes use `success/detail/error/data`; check HTTP status **and** `success`. Respect 429/Retry-After, stop repeated authentication attempts on 401/403, and retain stale snapshots as read-only on offline/5xx. One user-initiated request sequence per action, serialized config reads/writes, bounded body size and cancellation on profile switch; never truncate a configuration to fit a local buffer. PUT documentation shows returned `data.userData`, but Store's `updateUser` currently returns `void`; never depend on that field. Follow successful PUT with a fresh GET. No conditional-write revision or ETag precondition was found on User PUT. GET-before-PUT reduces conflicts but cannot guarantee atomic exclusion of another editor.

## 4. Safe linkage, secrets and writes

### Detect and bind

1. Reuse manifest already delivered to `addons_manifesto_lido_base`; snapshot list identity under existing lock. Match default AIO ID and user suffix plus `/stremio/.../manifest.json` shape. Name/logo alone is insufficient; forks/custom IDs become candidates requiring explicit instance selection and status/schema confirmation. Network only after user opens/connects area.
2. Parse installed URL with existing normalization; preserve scheme/host/port/path prefix and variant in opaque form. Support `/stremio/{uuid}/{I}/...`, `/stremio/u/{alias}/...`, `/v/{ids}` and `?v=`. Alias redirect may reveal full secret URL: suppress logging, bounded redirects, same verified origin/prefix policy, no Authorization forwarding across origin. Cross-origin alias requires explicit relink to destination before credentials.
3. Bind account + Nuvio profile + instance + configuration identity; variant is recorded as viewing context. Explain **GET/PUT edits base configuration shared by all its installs**, even when selected install uses a variant. Derived/primary-profile addon lists do not automatically authorize editing another person's config. Capture account/profile/session generation for every job and reject late results after switch/logout/removal.
4. Do not derive raw password from I. Current main requires C for User reads and writes. Offer manual masked raw-password unlock for session; generic QR lets user manage on phone instead. An older fixture may prove different auth, but never infer it from docs alone or change servers to make it work. Private/reverse-proxy login constraints remain visible, not bypassed.

### Storage and disclosure policy

- Keep existing installed URL as existing playback credential; store only a reference/opaque binding and non-secret display metadata for hub detection. Do not duplicate it into Settings blobs, `sync_push_provider_credentials`, analytics or new cloud records.
- Default editing authorization: **raw password only in memory**, discarded on leaving area, profile/account switch, timeout or logout. Full raw config/draft/undo snapshot also memory-only. Retain one undo snapshot during area session, at most 15 minutes after save; show expiry. Wipe buffers best-effort and release them. Relaunch requires unlock and fresh GET.
- No new persistent full-config/raw-password backup in 2.1 MVP. Offer configure-page export for durable recovery. `dados_gravar` is atomic storage, not encryption. Existing `debGravarArquivo` uses `mkstemp` + 0600 + rename; reuse its private-file pattern only if later persistence is explicitly selected. Filesystem permissions/sandbox do not equal encryption, especially IndexedDB. Persistent credentials/backups need supported platform secret storage or an explicit documented local-storage decision; no embedded encryption key.
- Reuse debrid masking presentation, but keep AIO credential domain separate. UUID/alias is masked too; short keys show only “configured”. Never display full manifest/config URLs or include I/raw C/session cookies/API keys/parent passwords in logs, diagnostics, screenshots, errors or fixtures. Provider HTTP errors may echo secrets: map to safe codes/text rather than rendering bodies. Sanitize nested URLs, headers and expressions, not just keys named `password`.
- QR contains **only non-secret configure URL**, never `/uuid/I/configure`, I, C, cookies or exported config. `qr.h` max is 134 bytes: if verified URL does not fit, use existing phone sheet to deliver a non-secret link or show plain address/instructions; never truncate or use external shorteners. Alias is a credential too, not a safe shortener.
- Existing `celular` input bridge is one-use/300 s and validates Host/Origin, but uses plain LAN HTTP. It is not confidential transport for new raw-management passwords or full configs. Reuse for non-secret link/input only in MVP; raw-password entry uses masked native keyboard. A secure phone-to-TV credential flow would require separate evidence, not an invented device-code endpoint. WGT cannot listen for this bridge.
- TLS certificate verification required for C and W; no downgrade, no credentials in query, no cross-host redirects. HTTP-only self-hosts can retain existing playback path but hub editing uses phone until secure transport exists. Avoid playback links/probing debrid media during diagnostics, preventing an extra provider IP/play action.

### Full-config write transaction, without a new transaction framework

1. Unlock and GET raw config **R0**; optionally GET effective config for explanation, never use merged result as PUT base. Keep original unknown members, nested option objects, ordering, opaque encrypted fields, parent config/strategies and optional-field absence. Edit only supported known leaves in a copy. Retain arbitrary JSON subtrees using existing `js`/`jsw` primitives; do not round-trip entire config through a reduced C struct. Reject oversized/truncated/invalid JSON before edit.
2. Review masked diff, configuration label and shared-client effect. Template input resolution and arbitrary changes remain in configure page. Show optional durable export instructions before high-impact preset/service/catalog changes. One in-memory complete R0 backup is mandatory before every Apply; failed allocation means no write.
3. On Apply, GET raw **R1** again. Compare canonical JSON semantically, ignoring object-key order only; preserve arrays and all values. If different from R0, stop and reload/review; no automatic merge. Supported-version normalization must not drop unknown fields. No background write or blind last-writer-wins retry.
4. Send one W with complete draft. Honor instance restrictions; protected config may reject because stripped accessKey requires O. Then retain draft and route to phone, never write an invented accessKey or silently strip parent/advanced fields to pass validation. Validation can fetch upstreams; report unavailable addon separately from wrong password.
5. After success **or timeout with uncertain delivery**, GET raw config. Compare to intended result using supported server normalization; show verified saved only on matching relevant values with preserved data. If response lacks `userData`, this is expected in inspected main, not a reason to resend. Nonmatching/failed verification means unknown outcome; require refresh, never repeat PUT automatically.
6. Undo reads current raw config and checks against last verified post-save snapshot. If unchanged, show same masked review and PUT complete R0, then verify. If changed by phone/another TV, stop and show conflict; never restore over it. Undo restores config only: it cannot reverse linked-account pushes, tracker side effects, password changes or history deletion. Those operations are outside MVP TV mutation scope.
7. Refresh installed manifest/resources/catalogs through existing addon path, update in-memory capability/cache generations and dependent discovery rows. Preserve installed URL/variant and normal account-to-TV sync. Config save normally keeps install URL, but catalog/resource manifest changes need refresh. Do not upload the whole Nuvio addon list; any future changed URL follows existing individual-add authorization.

**Residual race:** another editor can save between R1 and W; upstream offers no CAS. Show shared-config warning and ask user to avoid concurrent editing. Do not claim conflict-proof writes. A strict guarantee would require upstream revision/If-Match support; owner must accept this limitation or keep writes to phone on affected versions.

## 7. Risks and owner questions

| Risk | Required handling / remaining limit |
|---|---|
| Full PUT loses user's setup | Lossless raw snapshot, mandatory backup, narrow leaf edits, review, R1 conflict check, GET verification, guarded undo. No serializer that drops unknown config. Source lacks CAS; concurrency remains real. |
| Parent/variant writes change every device | Show base-vs-effective/selected variant before Apply. Preserve parent strategies; never flatten. Variant-specific editing via CEL stays phone-only initially. |
| False “saved” or duplicate request | Store response lacks config; read back. Timeout is uncertain, not failed. One in-flight write; no blind retry. |
| Credential exposure through URL/body/errors | Memory-only management session, origin/TLS checks, nested redaction, generic QR, no raw error bodies/export in reports. Existing installed playback link already has broad bearer power on older versions. |
| Undo overclaims recovery | One complete in-memory snapshot, visible 15-minute/session limit. Durable backup through phone export; no restart recovery promise. External effects cannot be undone by config restore. |
| Protected/private instance auth | C, O, I and J stay distinct. No operator/key bypass. Working phone configure fallback; native operator/SSO transport is not assumed. |
| API/schema drift and restrictions | Pinned source fixtures plus deployment version/capability check. Unknown or unverified config version read-only; preserve unsupported fields. 404/403/rate limit is feature/access state, not empty config. |
| Save invokes slow upstream/linked actions | Background jobs, cancellation generation, bounded request budget, safe upstream error, shared-client/linked-push notice. No work while drawing or on every focus event. |
| Wrong person/double scrobble | Explicit binding, direct-vs-delegated choice, no automatic tracking by addon detection. Reuse queue identity and MERCADO reconciliation. |
| Preset/template/URL trust | Treat content as untrusted data, no HTML/script evaluation. Respect host blocks and service/regex/SEL policies. Adding an external endpoint shows destination; never arbitrary background probes. |
| TV input/old GPU/WGT | Bounded native controls, virtualized lists, reuse Glass/solid geometry, cancel stale jobs, phone input fallback. WGT editing stays unavailable if required secure HTTP/storage/auth transport is absent. |

Owner questions to settle before implementation, with proposed defaults:

1. Does 2.1 require every advanced field editable by remote, or is every category reachable with phone-only authoring acceptable? **Default:** bounded TV controls plus QR for long text/regex/CEL/templates.
2. Accept shared-base-config writes with the upstream CAS limitation, explicit review and one-session undo? **Default:** yes only on fixture-verified versions; unknown versions read-only. Strict concurrent-write safety requires upstream change.
3. Is in-memory editing/undo sufficient, with phone export for durable backup? **Default:** raw management password and config never persisted; do not expand credential infrastructure in MVP.
4. Should settings edits affect all AIO clients by default, or should TV changes target an owner-created variant? **Default:** explicit shared-base notice; choosing/authoring a TV variant on phone. No automatic creation or overwrite of variants.
5. Which AIO persona/history source belongs to each Nuvio profile, and should AIO-owned history use existing Jellyfin connection or direct tracker delivery? **Default:** opt-in binding; one delivery route per tracker/person, no history import until chosen.
6. If protected instance editing needs operator/SSO login on phone, is read-only TV plus configure handoff acceptable for 2.1? **Default:** yes; no admin credentials stored in TV and no new auth gateway.
