# AIOStreams phone connection

The dashboard uses the app's HTTPS QR and expiring session pattern. It does not use the plain HTTP LAN text-entry helper for credentials. The shared worker serves `/aio/`; its `AioPair` Durable Object supplies a five-minute, memory-only inbox. No database, KV, analytics or credential logs are used.

The QR fragment contains a random 128-bit phone capability. Only its first eight hex characters identify the inbox; every operation also needs the full phone capability or the independent 128-bit TV capability. Both come from `/dev/urandom`, without a weak fallback. Credentials never enter a URL, query string, browser history or persistent browser storage. Refreshing the phone page requires scanning again.

The phone pins and displays the manifest's exact HTTPS origin and calls that origin's `/api/v1/user` with Basic authorization, redirects disabled, cookies omitted and a 12-second timeout. Only an official successful `data.userData` object permits delivery over HTTPS. The TV rejects an origin mismatch and independently checks `/api/v1/user` over verified HTTPS with redirects disabled. The inbox retains delivery in memory until the TV confirms the result, so a lost poll response can be retried. Confirmation is idempotent; the TV retries it up to three times and accepts authorization only after acknowledgement. The dashboard consumes authorization once and refreshes. Closing the screen or changing account/profile cancels acceptance; pending sessions expire after five minutes. Confirmation removes pending credentials immediately, retaining only status and an allowlisted error category until expiry.

The user's instance must permit the browser's cross-origin `/api/v1/user` request, including the `Authorization` header in the OPTIONS preflight response. The inspected official v2.37 source (`packages/server/src/middlewares/cors.ts`) allows only `Content-Type`; deployments retaining that default block phone verification. The instance operator must allow `Authorization` for the pairing site's origin (and permit GET/OPTIONS). This app must not proxy credentials through another origin or move them into a query string to bypass CORS. Browser errors cannot reliably separate CORS, TLS and network failures, so the phone groups those causes and distinguishes HTTP 401/403, 429/5xx, invalid responses and pairing-service failure. When the TV reports a terminal instance network/server failure, the phone requires a fresh QR instead of offering a retry on a stopped TV poller. Manual UUID/password entry remains the secondary action.

A package without an HTTPS `NV_REC_URL`, a worker without the routes/binding, or a configured pairing URL exceeding the existing QR generator's 134-byte limit shows pairing unavailable. QR regeneration immediately resets the displayed state; expiry/unavailability removes the stale code. The shared renderer caches the full supported URL, includes a four-module quiet zone and refuses to draw a previous texture when generation fails. The connection panel shows the instance origin instead of printing the private QR capability as text.

## Deployment required, not performed

1. Deploy the updated `servidor/recomendacoes` as the existing `nuvio-recomendacoes` worker, including `src/aiopair.js` and the already integrated `index.js` route/export changes. Existing memory-only sessions should be replaced by fresh QR sessions after deployment.
2. Apply Wrangler migration `v1-aiopair`, creating SQLite Durable Object class `AioPair`, with binding `AIOPAIR` from `servidor/recomendacoes/wrangler.toml`. No D1 SQL migration, KV namespace, new secret, or TV-site deployment is needed.
3. Ship a native TV build containing `src/aiopair.c`, `src/aiopair.h`, dashboard/i18n changes, and the existing HTTPS `NUVIO_REC_URL` build setting. Keep the worker's existing environment and bindings.

Validation: `bash tests/aiostreams.sh` exercises the shipped UI action, QR texture generation/cache/failure, real TV polling/validation code, shipped phone script, worker state machine and a local HTTPS fake instance. Fixtures cover origin rejection, wrong credentials, redirects, expiry, cancellation during creation/validation, network/server failure, malformed success responses, lost delivery/confirmation responses, one-time authorization receipt and log privacy. Password limits use UTF-8 bytes to match the TV buffers. The test uses synthetic data only. No real instance was contacted and no worker was deployed. Logs contain only operation, HTTP status and transport category; no response bodies, URLs, capabilities or credentials.
